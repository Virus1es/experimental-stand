# Проект НИР + практика + основа ВКР

## Экспериментальная платформа для исследования методов кэширования и предзагрузки данных

> Рабочая концепция проекта: **один развиваемый программный проект**,
> который начинается как прототип в рамках НИР, затем превращается в
> полноценный экспериментальный стенд на практике и в дальнейшем
> используется как программная основа экспериментальной части ВКР.

------------------------------------------------------------------------

# 1. Главная идея

Проект представляет собой программную платформу для **воспроизведения,
запуска и сравнительного исследования методов кэширования и предзагрузки
данных с применением машинного обучения**.

Главная логика:

``` text
НИР
  ↓
Программный прототип методов
  ↓
Практика
  ↓
Экспериментальный стенд
  ↓
ВКР
  ↓
Полноценное экспериментальное исследование
```

Это не три независимых проекта. Это **один проект, который постепенно
развивается**.

На каждом этапе добавляется новый уровень функциональности.

------------------------------------------------------------------------

# 2. Почему это соответствует текущей НИР

В НИР-2 уже определены:

-   исследуемые методы кэширования и предзагрузки;
-   четыре базовые метрики;
-   три типовых сценария применения;
-   итоговая классификация методов;
-   практическая направленность исследования.

Базовые метрики:

1.  задержка доступа к данным (`latency`);
2.  процент попадания в кэш (`hit rate`);
3.  процент промаха в кэше (`miss rate`);
4.  устойчивость работы при изменении нагрузки.

Типовые сценарии:

1.  высоконагруженные информационные системы;
2.  распределённые и периферийные вычислительные среды;
3.  системы с динамически изменяющимся поведением пользователей и
    нагрузкой.

Поэтому программный проект должен не просто демонстрировать алгоритмы, а
позволять **запускать их в сопоставимых условиях и получать измеряемые
результаты**.

# 3. Что именно представляет собой проект

У проекта две основные части:

``` text
                    CACHELAB
                       │
             ┌─────────┴─────────┐
             │                   │
          FRONTEND            BACKEND
             │                   │
       интерфейс          основная логика
       управления         экспериментов
       и визуализации          │
                               │
                    ┌──────────┼──────────┐
                    │          │          │
                  Cache       ML       Metrics
                 Methods    Methods     System
```

## Frontend

Frontend нужен прежде всего для взаимодействия пользователя с системой.

Через него можно:

-   выбрать метод кэширования;
-   выбрать сценарий эксперимента;
-   задать размер кэша;
-   задать интенсивность нагрузки;
-   выбрать тестовый набор данных;
-   запустить эксперимент;
-   остановить эксперимент;
-   посмотреть текущий статус;
-   посмотреть результаты;
-   сравнить несколько запусков;
-   построить графики;
-   просмотреть историю экспериментов.

Frontend **не выполняет основную вычислительную работу**.

Он является интерфейсом управления и визуализации.

------------------------------------------------------------------------

## Backend

Backend --- основная часть проекта.

Именно здесь находятся:

-   реализация алгоритмов кэширования;
-   реализация предзагрузки;
-   ML-модели;
-   генерация тестовой нагрузки;
-   запуск экспериментов;
-   работа с кэшем;
-   сбор метрик;
-   обработка результатов;
-   сохранение результатов;
-   API для frontend.

Упрощённо:

``` text
Frontend
   │
   │ HTTP
   ↓
FastAPI
   │
   ├── Experiment Manager
   │
   ├── Cache Strategies
   │
   ├── Prefetch Strategies
   │
   ├── ML Models
   │
   ├── Load Generator
   │
   └── Metrics Collector
          │
          ├── Redis
          └── PostgreSQL
```

# 4. Основной принцип работы

Пользователь открывает веб-интерфейс и создаёт эксперимент.

Например:

``` text
Метод:
Predictive Cache

Сценарий:
Высокая нагрузка

Размер кэша:
1000 элементов

Количество запросов:
100 000

Интенсивность:
500 req/s

Тестовый набор:
dataset_01
```

После нажатия:

``` text
[ Запустить эксперимент ]
```

Frontend отправляет запрос Backend.

Например концептуально:

``` http
POST /experiments
```

Backend создаёт эксперимент и запускает его.

Далее:

``` text
Генератор запросов
       ↓
Выбранный алгоритм
       ↓
Cache
       ↓
Обработка запроса
       ↓
Сбор метрик
       ↓
Сохранение результатов
```

После завершения frontend получает результат:

``` text
Latency:     42.3 ms
Hit Rate:    87.4 %
Miss Rate:   12.6 %
Stability:   91.2 %
```

И показывает его в виде таблиц и графиков.

# 5. Роль Frontend и Backend

Очень важно понимать разделение ответственности.

## Frontend

Frontend отвечает за:

``` text
Пользователь
    ↓
Интерфейс
    ↓
HTTP-запрос
    ↓
Backend
```

Frontend:

-   ничего не вычисляет самостоятельно;
-   не запускает ML-модели;
-   не управляет Redis напрямую;
-   не собирает системные метрики;
-   не проводит эксперимент.

Он только отправляет команды Backend и отображает результаты.

------------------------------------------------------------------------

## Backend

Backend:

``` text
HTTP API
   ↓
Experiment Manager
   ↓
Experiment Runner
   ↓
Algorithm
   ↓
Cache
   ↓
Metrics
   ↓
Database
```

То есть **основная исследовательская нагрузка находится на Backend**.

# 7. Алгоритмическая часть Backend

Предлагается сделать единый интерфейс стратегии.

Концептуально:

``` text
CacheStrategy
    │
    ├── LRU
    ├── LFU
    ├── FIFO
    ├── PredictiveCache
    ├── MLReplacement
    ├── CacheMissPrediction
    └── PrefetchStrategy
```

Это позволит менять алгоритм, не переписывая экспериментальную систему.

Например:

``` text
Experiment
    ↓
CacheStrategy
    ↓
LRU
```

или:

``` text
Experiment
    ↓
CacheStrategy
    ↓
PredictiveCache
```

При этом механизм измерения остаётся одинаковым.

В качестве baseline целесообразно использовать классические методы:

-   LRU;
-   LFU;
-   FIFO.

Они нужны как контрольная точка.

Например:

``` text

vs
```

Это позволит не просто показать абсолютные значения, а ответить на
вопрос:

> Насколько интеллектуальный метод отличается от классического алгоритма
> в одинаковых условиях?

Не обязательно сразу реализовывать все сложные методы.

Разумный подход:

### Первый уровень

Простые ML-модели:

-   Logistic Regression;
-   Random Forest;
-   другие относительно лёгкие модели.

Например:

``` text

       ↓
ML-модель
       ↓
Прогноз следующего обращения
       ↓
Prefetch
```

### Второй уровень

При необходимости:

-   LSTM;
-   PyTorch-модели;
-   reinforcement learning;
-   более сложные модели.

Главное --- не пытаться реализовать всю существующую научную
классификацию буквально.

В НИР классификация может включать пять групп, а программно можно
выбрать **репрезентативные методы** для экспериментов.

# 10. Пять групп методов

В текущем исследовании сохраняется пять групп:

1.  **Предиктивное кэширование и предзагрузка на основе анализа
    пользовательских запросов.**
2.  **Интеллектуальные политики замещения кэша.**
3.  **Методы прогнозирования cache miss.**
4.  **Интеллектуальное размещение данных и edge caching.**
5.  **Методы глубокого обучения, обучения с подкреплением и графовые
    модели кэширования.**

Программная система не обязана реализовать каждый возможный алгоритм
внутри каждой группы.

Лучше сделать:

``` text
Группа
   ↓
1–2 репрезентативных метода
   ↓
единый интерфейс
   ↓
единый эксперимент
   ↓
единые метрики
```

Redis используется как реальное кэш-хранилище.

Он позволяет приблизить эксперимент к практическому веб-приложению.

Схема:

``` text

   ↓
```

-   стратегию вытеснения;

-   интенсивность запросов.

При этом часть экспериментов можно проводить и на собственной реализации
алгоритмов, если это требуется для воспроизводимости исследования.

# 13. Метрики

Основной набор:

## Latency

Время обработки/получения данных.

Можно фиксировать:

-   average latency;
-   median;
-   p95;
-   p99.

Для научной части особенно полезно использовать не только среднее
значение.

------------------------------------------------------------------------

## Hit Rate

Доля запросов, обслуженных из кэша.

``` text
hit_rate = cache_hits / total_requests
```

------------------------------------------------------------------------

## Miss Rate

Доля запросов, для которых данных в кэше не оказалось.

``` text
miss_rate = cache_misses / total_requests
```

При обычной схеме:

``` text
miss_rate ≈ 1 - hit_rate
```

------------------------------------------------------------------------

## Stability

Показатель устойчивости работы метода при изменении нагрузки.

Например, можно исследовать изменение latency/hit rate при:

``` text
100 req/s
↓
250 req/s
↓
500 req/s
↓
1000 req/s
↓
2000 req/s
```

и анализировать, насколько сильно деградируют показатели.

------------------------------------------------------------------------

# 14. Генерация нагрузки

Для практического стенда предлагается использовать **Locust**.

Например:

``` text
100 пользователей
        ↓
250 пользователей
        ↓
500 пользователей
        ↓
1000 пользователей
```

Каждый профиль нагрузки запускает один и тот же набор методов.

Это позволяет сравнивать:

``` text
LRU при 1000 req/s
vs
ML при 1000 req/s
```

а не сравнивать результаты, полученные в разных условиях.

# 24. Реально ли это сделать за указанные сроки?

**Да, если не пытаться сразу сделать полноценную исследовательскую
платформу уровня production.**

Срок около 4,5 месяцев позволяет сделать MVP и постепенно его расширить.

Ключевой принцип:

> Сначала рабочий эксперимент без красивого интерфейса, затем интерфейс
> и инфраструктура.

Неправильный порядок:

``` text

↓
потом дизайн
↓
потом авторизация
↓
потом графики
↓
потом алгоритмы
↓
времени на эксперименты нет
```

Правильный порядок:

``` text

↓
Один эксперимент
↓
Метрики
↓
Несколько алгоритмов
↓
Автоматизация
↓
API
↓
Frontend
↓
Docker
↓
Grafana
```

# 28. Как это связано с ВКР

Проект может стать программной частью ВКР.

Например:

### Теоретическая часть

Исследование:

-   методов кэширования;
-   методов предзагрузки;
-   ML-подходов;
-   метрик;
-   сценариев применения.

### Практическая часть

Разработка:

> экспериментальной платформы для сравнительной оценки методов.

### Экспериментальная часть

Проведение:

``` text
Метод A
Метод B
Метод C
        ↓
одинаковая нагрузка
        ↓
одинаковый набор данных
        ↓
одинаковый размер кэша
        ↓
метрики
        ↓
сравнение
```

### Итог

Получение практических рекомендаций:

``` text
Если система высоконагруженная
→ метод X

Если распределённая / edge
→ метод Y

Если нагрузка динамическая
→ метод Z
```

Это непосредственно соответствует цели НИР-2 --- определить
сравнительную эффективность и области применимости методов и
сформировать практические рекомендации по их выбору.

# 29. Главное архитектурное правило

Нужно разделить **экспериментальную логику** и **интерфейс**.

Нельзя делать:

``` text
React/Next.js
   ↓
логика алгоритма
```

Правильно:

``` text
                Frontend
                   ↓
                 API
                   ↓
                Backend
                   ↓
```

Благодаря этому эксперимент можно будет запустить даже без Frontend:

``` bash

```

или через API.

Frontend --- только удобный способ управления системой.

# 31. Коротко: что мы строим

**Не просто веб-сайт.**

И не просто набор Python-скриптов.

Мы строим:

> **экспериментальную программную платформу, состоящую из Backend с
> алгоритмами кэширования, предзагрузки, ML-моделями, генерацией
> нагрузки и сбором метрик, а также Frontend для управления
> экспериментами, мониторинга и визуализации результатов.**

При этом:

``` text
                 CACHELAB
                    │
       ┌────────────┴────────────┐
       │                         │
    FRONTEND                  BACKEND
       │                         │
   управление              эксперименты
   визуализация             алгоритмы
   графики                  ML
   результаты               кэш
                            нагрузка
                            метрики
                               │
                ┌──────────────┼──────────────┐
                ↓              ↓              ↓
              Redis        PostgreSQL     Prometheus
                                               ↓
                                            Grafana
```

**НИР** создаёт ядро.

**Практика** превращает ядро в экспериментальный стенд.

**ВКР** использует стенд для полноценного экспериментального
исследования.
