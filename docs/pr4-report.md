## Аннотация

В работе представлен программный экспериментальный стенд CacheLab, предназначенный для воспроизводимого сравнения методов кэширования и предварительной загрузки данных веб-приложений.

Реализован HTTP-сервис на FastAPI с кэшированием в Redis, отдельный сервер-источник данных, механизм предиктивной предзагрузки с использованием машинного обучения, генератор конкурентной нагрузки Locust, а также инструменты автоматического запуска экспериментов и статистического анализа результатов.

Проведено сравнение классической стратегии LRU и LRU с ML-предзагрузкой в двух сценариях нагрузки. Для каждого сценария выполнено десять парных повторений. Дополнительно проведено десять A/A-сравнений для проверки корректности измерительного процесса.

В результате установлено, что применение ML-предзагрузки увеличивает долю попаданий в кэш приблизительно на 2–2,5 процентного пункта, однако не обеспечивает снижения задержки HTTP-ответа. В исследованных условиях p95 увеличился на 1,9 мс при пяти пользователях и на 4,9 мс при двадцати пользователях.

Полученные результаты демонстрируют необходимость комплексной оценки интеллектуальных методов кэширования с учётом не только hit rate, но и клиентской задержки, вычислительных расходов и дополнительной нагрузки на источник данных.

**Ключевые слова:** кэширование, LRU, Redis, машинное обучение, предварительная загрузка, FastAPI, Locust, Docker Compose, воспроизводимость, HTTP latency.

## 1. Исследовательская задача и гипотеза

### 1.1. Постановка исследовательского вопроса

В рамках предыдущей практической работы № 3 были сформулированы исследовательский вопрос, основные гипотезы, факторы эксперимента и требования к воспроизводимости.

Объектом исследования является процесс обслуживания обращений к данным веб-приложения с использованием ограниченного по ёмкости кэша.

Предметом исследования выступает влияние традиционных и интеллектуальных механизмов кэширования и предзагрузки на производительность веб-приложения.

Основной исследовательский вопрос:

_Как применение интеллектуальных методов кэширования и предзагрузки влияет на p95 времени HTTP-ответа веб-приложения относительно традиционных стратегий при стабильной, изменяющейся и высококонкурентной нагрузке и одинаковых ресурсных ограничениях?_

В качестве основной метрики выбрана задержка HTTP-ответа на уровне 95-го процентиля. Этот показатель характеризует время, за которое выполняются 95% запросов, и позволяет исследовать медленную часть распределения задержек.

Дополнительные показатели:

- средняя задержка HTTP-ответа;
- медианная задержка (p50);
- p99;
- доля попаданий в кэш (hit rate);
- количество запросов к серверу-источнику;
- количество выполненных и использованных предварительных загрузок;
- стабильность показателей между повторениями.

### 1.2. Исследовательская гипотеза

В ПР3 был установлен порог практически значимого улучшения: снижение p95 не менее чем примерно на 10%.

Для каждой пары прогонов относительное улучшение определяется формулой:

\[
I = \frac{p95*{\mathrm{LRU}}-p95*{\mathrm{LRU+ML}}}{p95\_{\mathrm{LRU}}}\cdot100\%.
\]

Положительное значение \(I\) означает уменьшение задержки, отрицательное — её увеличение.

Рассматриваются гипотезы:

- \(H_0\): типичное снижение p95 не превышает 10%;
- \(H_1\): типичное снижение p95 превышает 10%.

Цель настоящего этапа — проверить эту гипотезу на реализованном стенде и оценить величину эффекта с учётом случайной изменчивости результатов.

## 2. Реализация экспериментального стенда

### 2.1. Общая архитектура

Экспериментальный стенд включает следующие основные компоненты:

| Компонент         | Назначение                                            | Технология                |
| ----------------- | ----------------------------------------------------- | ------------------------- |
| Backend           | Обработка HTTP-запросов, работа с кэшем, предзагрузка | Python, FastAPI           |
| Redis             | Хранение закэшированных ресурсов                      | Redis 8.6.3               |
| Origin            | Имитация исходного сервера данных                     | HTTP-сервис               |
| ML Predictor      | Прогнозирование следующих обращений                   | scikit-learn              |
| Locust            | Генерация конкурентных запросов                       | Locust 2.46.0             |
| Experiment Runner | Управление запусками и сбор результатов               | Python                    |
| Analysis          | Статистическая обработка и визуализация               | pandas, SciPy, matplotlib |

Пользовательский HTTP-запрос поступает в backend. При наличии объекта в кэше он возвращается без обращения к origin. При отсутствии объекта backend получает данные с origin, добавляет их в кэш и возвращает клиенту.

В режиме ML дополнительно работает механизм прогнозирования будущих обращений. На основе истории запросов модель выбирает ресурсы, которые могут потребоваться в ближайшее время.

Предсказанные ресурсы передаются в очередь фоновой предзагрузки.

Предварительная загрузка использует тот же кэш, что и обычные пользовательские запросы. Поэтому предзагрузка может как снизить число последующих промахов, так и вытеснить уже закэшированные объекты.

### 2.2. Сравниваемые методы

**LRU.**

Least Recently Used — традиционная стратегия управления кэшем, при которой при заполнении доступной памяти вытесняется объект, не использовавшийся наиболее продолжительное время.

LRU используется в качестве базового метода, относительно которого оценивается дополнительная польза интеллектуальной предзагрузки.

**LRU + ML.**

Во втором режиме используется та же политика LRU, дополненная моделью предсказания будущих запросов.

Для прогнозирования применяется логистическая регрессия.

Основные параметры реализации:

| Параметр                               | Значение            |
| -------------------------------------- | ------------------- |
| Тип модели                             | Logistic Regression |
| Размер истории обращений               | 3                   |
| Порог вероятности предзагрузки         | 0,2                 |
| Максимальное число кандидатов          | 3                   |
| Количество фоновых исполнителей        | 2                   |
| Значение ограничения кэша по умолчанию | 50 000 байт         |

Модель обучается на начальной части трассы. Предзагрузка выполняется асинхронно.

Принципиально важно, что в этой работе ML не заменяет алгоритм LRU: она используется для предзагрузки объектов, а механизм вытеснения остаётся прежним.

### 2.3. Контейнеризация и ресурсные ограничения

Компоненты экспериментального контура запускаются через Docker Compose.

Для контейнеров заданы следующие ограничения:

| Сервис  |   CPU |     RAM |
| ------- | ----: | ------: |
| Backend | 2 CPU |   1 GiB |
| Redis   | 1 CPU | 512 MiB |
| Origin  | 1 CPU | 512 MiB |
| Locust  | 2 CPU |   1 GiB |

Для сервера-источника установлена искусственная задержка 50 мс.

Ограничение ресурсов необходимо, чтобы различные экспериментальные режимы работали в одинаковых условиях и результаты не зависели от произвольного изменения доступных ресурсов.

Использованная машина:

- архитектура AMD64;
- 16 логических процессоров;
- приблизительно 16,37 ГБ оперативной памяти;
- операционная система Windows;
- Python 3.10.11 на хосте;
- Locust 2.46.0 в контейнере.

Идентификаторы использованных Docker-образов записываются в манифесты экспериментов.

## 3. Воспроизводимость эксперимента

### 3.1. Конфигурационные файлы

Параметры запусков вынесены в JSON-файлы:

- `config/experiment_final_s1.json`;
- `config/experiment_final_s3.json`;
- `config/experiment.json`.

В них задаются:

- количество пользователей;
- число запросов прогрева;
- число измеряемых запросов;
- число повторений;
- максимальное время выполнения фазы;
- способ запуска Locust;
- режим fixed-count.

Это позволяет менять экспериментальные условия без изменения исходного кода оркестратора.

### 3.2. Команды воспроизведения

Команды выполняются из каталога `server`.

**Сценарий S1:**

```powershell
python -u -m scripts.run_experiment_pair `
    --config config/experiment_final_s1.json
```

**Сценарий S3:**

```powershell
python -u -m scripts.run_experiment_pair `
    --config config/experiment_final_s3.json
```

**A/A-тест:**

```powershell
python -u -m scripts.run_aa_experiment `
    --config config/experiment.json `
    --repeats 10
```

**Статистический анализ:**

```powershell
python -u -m scripts.analyze_experiments `
    --s1 results/pairs/20261128_002734_003820/manifest.json `
    --s3 results/pairs/20261128_010102_209100/manifest.json `
    --aa results/aa/20261128_013148_555673/manifest.json
```

Таким образом, проведение экспериментальной серии не требует ручного переключения методов и сбора показателей.

### 3.3. Очистка экспериментального состояния

Перед каждым запуском отдельного режима выполняются:

1. Остановка backend.
2. Очистка экспериментальной базы Redis.
3. Пересоздание backend-контейнера.
4. Проверка доступности HTTP API.
5. Проверка активного режима.
6. Проверка нулевых счётчиков.
7. Проверка SHA-256 входной трассы.

Для снижения влияния порядка выполнения в парных сериях режимы чередуются:

- LRU → LRU + ML;
- LRU + ML → LRU.

Это обеспечивает сбалансированный порядок сравнения.

При этом порядок не является случайно рандомизированным. Такая рандомизация запланирована для последующего расширения экспериментального протокола.

### 4.3. A/A-тест

A/A-тест предназначен для оценки изменчивости измерений при отсутствии реального различия между методами.

В обеих группах использовался обычный LRU.

Параметры:

- 5 пользователей;
- 13 прогревочных запросов на пользователя;
- 28 измеряемых запросов на пользователя;
- 10 парных повторений.

Разница определялась как:

\[
\Delta\_{AA}=p95_B-p95_A.
\]

Получены результаты:

| Метрика                         |            Значение |
| ------------------------------- | ------------------: |
| Число пар                       |                  10 |
| Средняя разница p95             |             −0,4 мс |
| 95% доверительный интервал      | [−1,169; +0,369] мс |
| Максимальная абсолютная разница |                3 мс |

Доверительный интервал включает нуль. Следовательно, систематическое отличие между двумя одинаковыми конфигурациями не обнаружено.

Однако отдельные различия достигают 3 мс, поэтому небольшое изменение p95 в одной экспериментальной паре нельзя автоматически интерпретировать как устойчивый эффект метода.

Полученная оценка шума относится к нагрузке с пятью пользователями и не может без дополнительной проверки переноситься на более высокую конкурентность.

### 4.4. Проверка генератора нагрузки

Во время предварительного тестирования с двадцатью пользователями выполнялся сбор показателей Docker.

В отдельных измерениях загрузка CPU контейнера Locust составляла приблизительно 6–36%, а используемая память — 45–51 MiB.

Значения CPU были ниже рекомендуемого для задания ориентировочного порога 80%.

Следовательно, в наблюдавшиеся моменты генератор нагрузки не демонстрировал очевидного насыщения процессора.

При подготовке ML-сервиса наблюдались более высокие значения загрузки CPU backend — около 190–210%. Они связаны с работой backend в период подготовки и не должны напрямую интерпретироваться как загрузка генератора.

Ограничение этой проверки состоит в том, что отдельные снимки `docker stats` не позволяют исключить кратковременные пики потребления ресурсов.

Для последующего исследования потребуется непрерывная регистрация загрузки контейнеров.

### 4.5. Стабильность результатов

В сценарии S1 p95 обычного LRU по десяти повторам составлял 60–61 мс.

Для LRU + ML значения p95 составляли около 62 мс.

В S3 наблюдалась более высокая изменчивость задержки, соответствующая большей конкурентности.

По последовательности результатов не выявлено очевидного устойчивого монотонного роста метрик от первого запуска к последнему.

При этом отдельный формальный тест временного тренда пока не проводился.

### 5.3. Статистический анализ p95

Для каждой пары вычислялась разность:

\[
d*i=p95*{ML,i}-p95\_{LRU,i}.
\]

Средняя разность определялась по десяти парным повторениям.

95% доверительный интервал рассчитывался с использованием распределения Стьюдента:

\[
CI*{95}=\bar d\pm t*{0.975,n-1}\frac{s_d}{\sqrt n},
\]

где \(n=10\), \(\bar d\) — средняя разность, \(s_d\) — стандартное отклонение парных различий.

Дополнительно рассчитывался стандартизованный размер эффекта:

\[
d_z=\frac{\bar d}{s_d}.
\]

**Таблица 2 — Статистические результаты.**

| Показатель                         |        S1 |        S3 |
| ---------------------------------- | --------: | --------: |
| Средняя разница p95 (ML − LRU)     |   +1,9 мс |   +4,9 мс |
| Нижняя граница 95% CI              | +1,674 мс | +3,233 мс |
| Верхняя граница 95% CI             | +2,126 мс | +6,567 мс |
| Стандартизованный эффект \(d_z\)   |    ≈+6,01 |    ≈+2,10 |
| Среднее относительное снижение p95 |    −3,16% |    −6,54% |
| Пар с увеличением p95              |  10 из 10 |  10 из 10 |

Во всех десяти парах S1 и десяти парах S3 вариант LRU + ML имел более высокий p95.

Доверительные интервалы средней разности полностью находятся выше нуля.

Таким образом, для исследованных условий установлено устойчивое увеличение p95 при добавлении ML-предзагрузки.

При этом величина стандартизованного эффекта не должна интерпретироваться отдельно от абсолютной разницы в миллисекундах.

### 5.5. Анализ нагрузки на origin

Помимо пользовательских запросов при ML-предзагрузке сервер-источник обрабатывает дополнительные запросы для предварительного получения объектов.

Поэтому:

\[
N*{\mathrm{origin}}=N*{\mathrm{misses}}+N\_{\mathrm{prefetch}}.
\]

В S1 число обращений к origin выросло с 222,0 до 231,5 за прогон.

В S3 — с 356,8 до 387,6.

Относительное увеличение составило приблизительно:

- S1: +4,28%;
- S3: +8,63%.

Это показывает, что увеличение доли попаданий в кэш было достигнуто ценой дополнительной работы сервера-источника.

Для нормированного сопоставления при различном числе запросов следует использовать количество обращений к origin на 1000 пользовательских запросов.

В S1 показатели равны 222,0 и 231,5, в S3 — приблизительно 223,0 и 242,25 для LRU и LRU + ML соответственно.

### 5.6. Интерпретация результатов

В S1 ML-предзагрузка повысила hit rate, однако привела к увеличению медианной и p95-задержки.

В S3 средняя задержка практически не отличалась между режимами, но p50 и p95 оказались выше для LRU + ML.

Таким образом, изменение среднего времени ответа и изменение верхних процентилей могут иметь разную направленность.

Дополнительная работа прогнозирующего механизма, операции с очередями, асинхронная предзагрузка и конкуренция за ресурсы могут влиять на задержку клиентского запроса.

При этом имеющихся измерений недостаточно, чтобы количественно разделить вклад каждого из перечисленных факторов. Для установления конкретной причины необходимы отдельные инструментальные измерения времени инференса, операций кэша и очередей.

Результат демонстрирует принципиальную особенность интеллектуального кэширования:

**повышение hit rate не гарантирует уменьшения времени ответа веб-приложения.**

## 6. Сопоставление с научными исследованиями

В предыдущей работе ПР3 были рассмотрены научные публикации, посвящённые интеллектуальному кэшированию и предварительной загрузке.

### 6.1. Интеграция предзагрузки и кэширования

Yang и Zhang [1] исследовали использование моделей предсказания для совместного управления веб-кэшированием и предварительной загрузкой.

Авторы рассматривали не только долю попаданий в кэш, но и относительную задержку и дополнительные затраты на передачу данных.

Этот подход соответствует необходимости одновременно учитывать клиентскую производительность и ресурсную стоимость предварительной загрузки.

В то же время модельная метрика задержки из статьи не эквивалентна p95 реального HTTP-сервиса, поэтому прямое численное сопоставление результатов некорректно.

### 6.2. Интеллектуальные политики кэширования

В исследовании Torabi, Khazaei и Litoiu [2] предложена стратегия HR-Cache, использующая машинное обучение для выбора объектов, подходящих для хранения в edge-кэше.

Авторы оценивали эффективность через байтовые показатели и экономию WAN-трафика относительно традиционных алгоритмов.

В отличие от HR-Cache, в CacheLab машинное обучение используется не для замены политики вытеснения, а для организации предзагрузки.

Поэтому различия в результатах объясняются в том числе различием оптимизируемых метрик и архитектур.

### 6.3. Стоимость интеллектуальной предзагрузки

В работе Wong и соавторов [3] исследуется сочетание ML-admission и предзагрузки в системах хранения с флеш-кэшированием.

Авторы рассматривают снижение нагрузки на медленные устройства хранения с учётом дополнительных операций.

Для настоящей работы принципиальное значение имеет необходимость учитывать стоимость работы интеллектуального механизма, а не только количество попаданий в кэш.

При этом результаты для SSD-кэшей нельзя непосредственно переносить на p95 HTTP-ответов.

### 6.4. Общий вывод

Сравнение с литературой показывает, что эффективность интеллектуального кэширования существенно зависит от:

- характеристик нагрузки;
- ёмкости кэша;
- качества прогнозов;
- накладных расходов модели;
- стоимости обращения к источнику;
- оптимизируемой метрики.

Полученный в CacheLab отрицательный результат по p95 не противоречит самому принципу интеллектуальной предзагрузки, но ограничивает область её применимости в исследованной конфигурации.

## 7. Угрозы валидности и ограничения

В рамках исследования выявлены следующие ограничения.

| Угроза                              | Проявление                                  | Планируемое решение                    |
| ----------------------------------- | ------------------------------------------- | -------------------------------------- |
| Ограниченная внешняя валидность     | Используется одна синтетическая трасса      | Добавление реальных трасс              |
| Ограниченный набор методов          | Проверена одна ML-модель                    | Подключение дополнительных моделей     |
| Ограниченная вариативность нагрузки | Измерены S1 и S3                            | Реализация S2 и других профилей        |
| Зависимость от ёмкости кэша         | Не проверены исходные уровни 5% и 20%       | Факторный анализ ёмкости               |
| Эффект порядка запусков             | Порядок сбалансирован, но не рандомизирован | Случайный порядок с фиксированным seed |
| Ограниченная проверка генератора    | Использовались выборочные снимки Docker     | Непрерывный мониторинг ресурсов        |
| Шум при высокой нагрузке            | A/A выполнен только для пяти пользователей  | Дополнительный A/A для S3              |
| Точность процентилей                | Используется приближённый алгоритм Locust   | Сохранение индивидуальных задержек     |

| Ограничение модели origin           | Постоянная искусственная задержка           | Разные профили задержек                |

Отдельно следует учитывать, что использование одинаковой трассы обеспечивает сопоставимость методов, но не гарантирует переносимости результата на произвольное реальное веб-приложение.

Для более общих выводов необходимо исследовать несколько типов нагрузки и несколько моделей машинного обучения.

## 8. Выводы и дальнейшее развитие

### 8.1. Основные результаты работы

В ходе выполнения практической работы:

1. Реализован контейнеризированный экспериментальный стенд CacheLab.
2. Настроен автоматический запуск экспериментов через конфигурационные файлы.
3. Обеспечено сохранение исходных результатов и метаданных.
4. Реализована проверка идентичности нагрузки.
5. Проведён A/A-тест из десяти парных повторений.
6. Выполнены два основных сценария с десятью парными повторениями каждый.
7. Выполнена статистическая обработка результатов с доверительными интервалами.
8. Подготовлены сравнительные графики.

По результатам экспериментов установлено:

- при использовании ML-предзагрузки hit rate увеличился приблизительно на 2–2,5 процентного пункта;
- p95 увеличился на 1,9 мс в S1 и на 4,9 мс в S3;
- число запросов к origin увеличилось в обоих сценариях;
- гипотеза о снижении p95 более чем на 10% не получила подтверждения.

Это означает, что используемый вариант интеллектуальной предзагрузки не продемонстрировал практического преимущества по основной метрике в текущих условиях.

При этом стенд показал способность обнаруживать, измерять и воспроизводимо оценивать такие эффекты.

### 8.2. Перспективы развития для ВКР

В дальнейшем планируется:

1. Расширить набор моделей машинного обучения.
2. Добавить несколько политик замещения кэша.
3. Провести эксперименты с различной ёмкостью кэша.
4. Реализовать сценарии с изменением популярности объектов.
5. Использовать реальные трассы обращений.
6. Добавить измерение стоимости инференса.
7. Исследовать влияние глубины предзагрузки и порога вероятности.
8. Ввести непрерывный мониторинг ресурсов контейнеров.
9. Выполнить расширенную статистическую проверку повторяемости.
10. Дополнить визуализацию распределением индивидуальных задержек HTTP-ответов.

Архитектура CacheLab допускает такое расширение без полной переработки экспериментального контура.

Главным направлением будущего исследования станет определение условий, при которых интеллектуальная предзагрузка обеспечивает не только увеличение hit rate, но и реальное улучшение клиентской производительности веб-приложения.
